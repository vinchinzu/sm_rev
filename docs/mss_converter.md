# MiniSaveState Converter: Corresponding Start vs Mini-Authored

This document explains the difference between **corresponding start** states (created by the converter) and **Mini-authored** states (created by Mini itself).

## Quick Summary

- **Corresponding start** (.mss from converter): Same WRAM bytes as emulator savestate, but **Mini physics may diverge**
- **Mini-authored** (.mss from Mini): Generated entirely by Mini's runtime, **guaranteed deterministic** for Mini physics
- **Purpose**: Corresponding start lets Mini and emulator begin from the same WRAM, useful for comparing behavior, NOT for TAS-correct Mini states

## Tool: `tools/mss_converter.py`

Converts stable-retro / snes9x `.state` files to MiniSaveState `.mss` format.

### Usage

```bash
# Convert a .state file to .mss
python3 tools/mss_converter.py input.state -o output.mss

# Use with sm_rev_predict
./sm_rev_predict --load-state output.mss < input.json
```

### What It Does

The converter:
1. Parses the `.state` file (gzip-decompressed `#!s9xsnp:` format)
2. Extracts the WRAM block (128KB)
3. Creates a MiniSaveState template using `generate_mss_fixture`
4. **Overlays** these WRAM addresses from the source:
   - `$0AF6` - samus_x
   - `$0AF8` - samus_x_sub
   - `$0AFA` - samus_y
   - `$0AFC` - samus_y_sub
   - `$0A1C` - pose
   - `$079B` - room_id
   - `$09C2` - energy
5. Writes the modified `.mss` file

### Frame 0 Guarantee

When loading the converted `.mss` with `sm_rev_predict --load-state`:
- **Frame 0** (pre-step) will exactly match the overlaid WRAM addresses
- Frame 0 is captured **before** any `MiniStep` call
- This creates a "corresponding start" between Mini and the emulator

## Corresponding Start vs Mini-Authored

### Corresponding Start (Converter Output)

```
Source: Emulator savestate (.state file)
Created by: tools/mss_converter.py
WRAM: Copied from emulator
Physics: May diverge from emulator immediately after frame 0
Use case: Compare Mini vs emulator behavior from same starting state
NOT TAS-correct: Mini physics ≠ emulator physics
```

**Example:**
```bash
# Convert emulator state
python3 tools/mss_converter.py emulator_save.state -o corresponding.mss

# Frame 0 will match emulator's $0AF6/$0AF8/$0AFA/$0AFC
# Frame 1+ may diverge due to physics differences
```

### Mini-Authored (Native Mini State)

```
Source: Mini runtime (generate_mss_fixture or MiniSaveState())
Created by: Mini's own code
WRAM: Generated by Mini
Physics: Guaranteed deterministic for Mini
Use case: Golden fixtures, rollback tests, Mini-only replays
```

**Example:**
```
tests/fixtures/landing_site_spawn.mss
  - Created by generate_mss_fixture.c
  - Pokes x=128, y=176, room=0x91F8, health=99 into g_ram
  - Then calls MiniSaveState to snapshot
  - This is Mini-authored, NOT a corresponding start
```

## Key Differences

| Aspect | Corresponding Start | Mini-Authored |
|--------|-------------------|---------------|
| Source | Emulator savestate | Mini runtime |
| WRAM origin | Emulator RAM | Mini g_ram |
| Frame 0 match | Exact at specified addresses | N/A (Mini-only) |
| Determinism | Frame 0 only | All frames |
| TAS-correct | No | For Mini, yes |
| Use with emulator | Comparable | Incompatible |

## Testing

The CI test (`tests/test_mss_converter.py`) verifies:
1. **Synthetic WRAM overlay**: Creates a fake WRAM buffer, overlays onto template, verifies round-trip
2. **No ROM required**: Uses synthetic data, not actual game states
3. **Key addresses verified**: All 7 required addresses are checked

Run tests:
```bash
python3 -m pytest tests/test_mss_converter.py -v
```

## Limitations

### What Corresponding Start Does NOT Guarantee

- **Physics parity**: Mini uses different collision, movement, and timing logic than the emulator
- **TAS playback**: A TAS replay from the emulator will likely diverge in Mini
- **Long-term accuracy**: Differences compound over frames
- **Full WRAM match**: Only the 7 key addresses are overlaid, not all 128KB

### When to Use Each

**Use Corresponding Start when:**
- Comparing Mini vs emulator behavior from a known state
- Debugging physics differences
- Starting from a specific emulator checkpoint

**Use Mini-Authored when:**
- Creating golden test fixtures
- Rollback/replay testing within Mini
- Deterministic Mini-only work
- You need guaranteed frame-perfect reproducibility

## Implementation Details

### MiniStateSnapshot Structure

```c
typedef struct MiniStateSnapshot {
  uint32 magic;                              // 0x4D53534D "MSSM"
  uint32 version;                            // 4
  MiniGameState game;                        // Variable size
  MiniStubsSnapshot stubs;
  MiniPpuSnapshot ppu;
  uint8 ram[0x20000];                        // 128KB WRAM (overlaid by converter)
  uint8 sram[0x2000];                        // 8KB SRAM
  bool use_my_apu_code;
  bool host_debug_flag;
  int snes_frame_counter;
  uint16 installed_bug_fix_counter;
} MiniStateSnapshot;
```

The converter finds the `ram[]` array by searching backwards from the end of the file (WRAM is followed by SRAM and trailing fields).

### WRAM Address Overlay

The converter overlays the **entire 128KB WRAM** from the source `.state` into the template's `ram[]` array. This ensures that the 7 key addresses (and any other addresses Mini reads) match the emulator's state at frame 0.

However, only these 7 addresses are explicitly verified by the test and documented as the "corresponding start" contract.
